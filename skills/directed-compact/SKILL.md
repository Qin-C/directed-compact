# directed-compact

压缩是一次模型总结,只读得到当前对话,读不到文件。所以要留下的内容必须先出现在对话里,再由指令点名。这份技能不依赖任何插件或外部系统。

## 什么时候做

- 用户要求写检查点或压缩。
- 上下文占用偏高,手上这件事做到了一个能停的地方。占用多少算高由用户定,也可以按经验在一半左右开始留意。比例会随版本和模型变,不要写死。
- 不要为了压缩打断一件马上就做完的事:先做完,同一轮接着写检查点。
- 不要只说「下一步写检查点」然后停下。决定做了就在这一轮做完。

### 压缩,还是换一个新会话

按顺序问,第一个答「是」的定方向:

| 问题 | 是 |
|---|---|
| 换负责人、换方向、换代码仓库? | 换新会话 |
| 某个设计正在和用户来回收敛? | 压缩(换会话会把过程压成结论) |
| 一波事已经收口,产出已经落到文件或提交上,下一步是新的一波? | 换新会话 |
| 压缩后用户仍要反复重说之前说过的事,或压缩后的摘要本身已经很大? | 换新会话 |
| 手上这件还在做? | 压缩 |

选择换新会话时,仍然写检查点,把全文作为新会话的开场材料。

## 第 1 步:写检查点

用一次写文件操作把全文写到项目里,例如 `checkpoints/<日期>-checkpoint.md`,这样全文就进了对话。文件只是副本,方便压坏时人回读,也供脚本对账,它不是送给压缩的手段。

检查点贵在来回次数,不在长度。一条消息写完,不要逐项分几轮查,也不要写完再读回来核对。写定后要改就做局部修改,并把改动贴进回复;用局部修改拼出来的检查点,要把全文再贴进回复一次。

模板(小节开头的符号不要改,对账脚本靠它们切段):

```markdown
> Checkpoint: <当前时间>
本次必留:原话 N 条 · 未决 N 行 · 警告 N 条 · 被否选项 N 个 · 在跑的子代理 N 个
## 🔴 原话拍板(逐字,不改写)
- 「用户的话」→ 已做 / 未做,日期
## ⚠ 未决
| 事项 | 建议 | 状态 |
|---|---|---|
## 🚨 警告
1. 一句内容 + 判据
## 🧠 被否掉的选项与为什么否
- 不做 B,因为 C
## ✅ 已排除(有证据,不用重查;排查类任务才写)
## 📌 现场
命令、关键数字、路径、标识符;会话名称;压缩次数
## ▶️ 下一步
1. 具体动作;没有活就写「无,等用户派」
## 🛰 在跑的子代理(有才写)
| 派出时间 | 任务 | 产物 | 断言 |
|---|---|---|---|
## ⏱ 只活在本会话的东西(有才写)
定时提醒、临时文件、后台任务,每条带现查命令
```

写法守则:

- `## ⚠` 和 `## 🚨` 每次从当前事实重建,不在旧的上面追加。`## 🔴` 只追加,每条带日期。
- 用户的长期要求(回复语言、哪类事必须先问)要抄进 `## 🚨`,哪怕这一段没有再提。
- 警告写内容,不写标题。写完问一句:光凭这一行,接手的人动得了手吗?
- 不要写「见上面第 3 条提案」这种指回对话的引用,压缩后对话就没了。
- 被否选项只写一行结论,不写尝试过程。
- 要保的话放在主句里。压后活下来的是主句,掉的常是括号里的内容。一个分句只说一件事。
- 路径、行号、标识符原样写,不翻译、不概括。
- 下一步里写到某个工具或命令时,照项目文档抄。压后这一句会被当成事实照做。
- 会被后续动作改掉的数字,标上测量时间,或者不写。
- 「本次必留」的条数在全文写完后现数,不要先定数再往里填。
- 自检:把这份检查点盖住对话,还能接着干吗?不能就补。

## 第 2 步:给出 /compact 指令

技能不能替用户执行 `/compact`。在回复里给用户一整行,紧前面写明动作:「粘贴下面这一整行,回车」。

```text
/compact 逐字保留上文检查点:「本次必留」这一行原样;① 🔴 每一条原话拍板(含日期)共 N 条;② ⚠ 未决表每一行(事项/建议/状态)共 N 行;③ 🚨 每条警告的内容而不是标题,共 N 条;④ 🧠 被否掉的选项与为什么否共 N 个,<点名正在收敛的方案>;⑤ 📌 的命令、数字、行号、路径、标识符原样,不许概括;⑥ 🛰 每个在跑子代理的验收断言;⑦ ▶️ 下一步原样;每一条都写出内容,不要用「同上」「略」「共 N 条」代替。可丢:工具输出原文、被否掉的中间尝试过程、已修好的报错堆栈、截图描述。
```

- N 换成实际条数。条数和「内容不是标题」要成对出现,只有条数可能条数全对、内容只剩标题。
- 只点名保什么、几条,不要把判据全文搬进指令,内容已经在对话里。
- 指令里点名要保什么,不要让模型重抄上一次摘要。
- 不提供不带指令的压缩。
- 告诉用户:压完回一句话,说什么都行。压缩本身不会唤醒模型。

回复第一句写结论、理由和条数,例如:「建议现在压缩,手上这件还没做完;必留共 N 条,检查点副本在 `<路径>`。」

## 第 3 步:压后对账

用户压完回话后,先做这几件,再做别的:

1. 找转录:通常在 `~/.claude/projects/<项目目录名>/` 下,取修改时间最新的 `.jsonl`。同一目录有多个会话在跑时,要核对内容确认是这一条。
2. 有脚本时运行(`<仓库>` 是本仓库所在目录):

   ```bash
   python3 <仓库>/scripts/compare-summary.py <transcript.jsonl> <checkpoint.md>
   python3 <仓库>/scripts/count-compactions.py <transcript.jsonl>
   ```

   `compare-summary.py` 退出码:0 没有丢或残,1 有丢或残,2 输入有问题。没有脚本时,逐段对照检查点和当前摘要。
3. 给用户一张表:

   | 必留 | 压前几条 | 压后还剩 | 丢了哪条 · 找回没有 |
   |---|---|---|---|

4. 丢了或残了的,到转录里找原文,补进当前上下文。只剩一个词的条目算丢。
5. 脚本标「判不了」的人工看。摘要可能把数字更新成压前最后几轮的新事实,先分清是更新了还是丢了。
6. 不要过度相信结果。锚点在只说明标识符活着,不说明意思没走样;零丢失也不说明检查点写对了,写错的照改。
7. 摘要的状态描述两个方向都可能错。写着「已推送、已合并」的,用实际命令核对;写着「还没做」的有副作用动作(发消息、推送),先确认确实没做,避免重复。
8. 检查点里记录的别人的状态只是快照,据此行动前先现查。

## 第 4 步:接着干

对账后,一句话说明「接着做下一步第一条:<动作>」,然后就在这一轮开始做,不等用户再说一句。

只有两个例外:下一步写的是「无,等用户派」,报告对账结果后停下;用户这次明确派了别的活,按用户说的做,并说明原来的下一步先搁置。

## 边界

- 不要把「保留什么」写成「去读哪个文件」。压缩这一步读不到文件。
- 对账和报告出现异常时要说出来。「坏了」和「悄悄降级了」在输出上看起来一样。
